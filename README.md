# Штаб

Центр компании: единая витрина показателей и сайт с разделами подразделений поверх неё.

Три слоя:

1. **Сборщики** (`collector/`) — ночные скрипты складывают точки показателей в витрину через `POST /api/ingest`.
   Раскладка источников (таблицы, колонки) не хранится в коде — приходит в переменных окружения.
2. **Витрина** (`schema.sql`, Cloudflare D1) — одна запись: показатель, период, срез, факт; планы — рядом.
   Реестр показателей — `metrics.json`.
3. **Сайт** (`site/`, Cloudflare Pages + Functions) — API витрины, общий экран и разделы с персональными логинами.

API (доступ проверяется отдельно для каждой операции):

- `POST /api/ingest` — пачка точек, идемпотентно
- `GET /api/points?metric=a,b&ptype=day&from=&to=&dim=` — точки
- `GET /api/metrics`, `POST /api/metrics` — реестр
- `GET /api/status` — прогоны и покрытие

Документы, раскладка и настройка — в приватном репозитории.

Сборщик сделок сверяет месяц отчёта и отметку `export_date` до записи точек. `REPORT_SHEET_ID` в переменных GitHub Actions указывает на действующую месячную таблицу amo-export. При смене месяца сборщик ищет единственный отчёт той же серии на Google Drive. `REPORT_STAMP_RANGE` задаёт диапазон из двух колонок с ключом `export_date` и датой успешной выгрузки. При устаревшем отчёте, неоднозначном выборе или отсутствии отметки сбор останавливается до записи. Исторический пересчёт запускается через `shtab-collect.yml` с `deals_only=1`, датами `from` и `to` и при необходимости `report_sheet_id` за соответствующий месяц.

## Проверки P1

Нужны Node.js 22.14+ и Python 3.12+. Установка пакетов, секреты и доступ к боевым сервисам не требуются.

```sh
node --experimental-sqlite --test tests/p1-security.test.mjs
python -m unittest discover -s tests -p "test_*.py" -v
```

Серверные тесты запускают настоящие обработчики на SQLite в памяти с адаптером интерфейса D1. `batch` выполняется одной транзакцией; SQL-триггеры имитируют ошибку в середине загрузки. KV и модель заменены тестовыми реализациями. Это не проверка удалённого Cloudflare D1. Для тестовой схемы учтено восстановление перезаписанной миграции в `schema20.sql`.

Браузерная проверка изоляции:

```sh
node --experimental-sqlite tests/browser-isolation.mjs
```

Открыть `http://127.0.0.1:8769`: ожидается `PASS: both frames isolated; zero API requests`. Проверяются iframe с sandbox и iframe, защищённый только CSP-заголовком; ссылка внизу проверяет прямое открытие. Все проверки должны быть `true`. Стенд содержит только искусственные данные, завершение — Ctrl+C.

## Изменения доступа и импорта

- Вход только по персональной сессии: пароль аккаунта или Telegram. Старая `okk_auth` не принимается, `/__setup` отключён. Перед выкладкой нужен рабочий личный аккаунт администратора. Старое значение `password` в KV больше не используется; его можно удалить после перехода на личные аккаунты.
- Токен сборщика не является администратором. Сохраняются явно разрешённые служебные операции; через общий слой доступны только GET `points`, `metrics`, `status`, `prep`, `pings`. Управление пользователями требует личной сессии администратора. Пинги находят адресата через `GET /api/pings?mode=recipient&match=…`, получая только один Telegram ID без списка аккаунтов и прав.
- API показателей, данных разделов и контекст ИИ учитывают права на исходные разделы. Итоги маркетинга, включающие закрытый источник, не выдаются; точный разрешённый источник можно запросить через `dim`. Черновики и промпты доступны только редакторам. Справочник `knowledge`, не имеющий разметки прав, включается в контекст ИИ только администратору.
- Собственные HTML-виды получают снимок разрешённых данных через совместимый `fetch(DATA_URL)`. Произвольные сетевые запросы, cookies/storage и DOM родителя недоступны. Защита CSP действует также при прямом открытии вида.
- Изменение отпусков требует уровня 2 одновременно на `hr.team` и `hr.leave`. Просмотр HR не даёт записи. Удаление сотрудника, которое каскадно удаляет его отпуска, требует тех же прав; правка личных полей требует уровня 2 на `hr.team`.
- Полная замена `prep_alumni`, `yt_paid`, `yt_leads` валидируется до записи и выполняется одной транзакционной D1 batch. Максимум — 20 000 строк в каждом наборе; превышение или невалидная строка отклоняются целиком. JSON-параметры разбиваются по размеру, без обрезки списка. Пустой массив явно публикует пустой набор.
- Полный сбор YouTube отправляет `yt_leads_replace: {rows: [...]}` вместе с `yt_paid: {replace: true, rows: [...]}` одним запросом. Старый `yt_reset` отклоняется. Инкрементальные `yt_leads`/`yt_drop` сохраняются. При неуспешной полной замене можно повторить весь запрос.

Миграции базы для этих изменений не нужны. Сервер и обновлённые сборщики YouTube/пингов нужно выпускать согласованно: сначала сервер, затем сборщики; до завершения выкладки сервера не запускать новый полный сбор YouTube. Полная сборка сайта через `cf-build.sh` требует приватных источников и не входит в автономные тесты.

После публикации можно вручную запустить GitHub Actions `P1 release verification`: он повторяет регрессионные тесты и проверяет рабочие API, используя существующий секрет `SHTAB_TOKEN`. Проверка не меняет рабочие данные и не отправляет уведомлений; в журнал попадают только названия проверок и HTTP-статусы. Затем запускается обычный YouTube `mode=inc`, а пинги при необходимости проверяются с `dry=1`.
